# Existing Behavior — NSL Bank (CSE241)

The source of truth for the migration. Everything here was derived from
`scz225zwart/scz225/App.java` and `Database.java`; line numbers refer to those
files. The original Oracle database (`edgar1.cse.lehigh.edu`) and its DDL and
data are **not** in this repository, so the schema below is a reconstruction.

Two ISA hierarchies: `account → checking | savings` and `card → credit | debit`.

### PostgreSQL incompatibilities

1. **`limit` is a reserved word in PostgreSQL** (it wasn't in Oracle). The column keeps its name but must be written `"limit"` in SQL. Tested in `tests/db/original-queries.test.ts`.
2. **Generated keys**: Oracle's `getGeneratedKeys(new String[]{"account_id"})` becomes `INSERT ... RETURNING account_id`.
3. Mixed-case table names (`Account`, `Loan`) work unchanged because neither database quotes them.

Every other statement in `Database.java` runs unchanged (verified by tests).

## 2. Operations

### Employee menu (read-only)
| Option | Query |
|---|---|
| View all customers / cards / accounts / transactions / loans | `SELECT * FROM <table>` |

### User menu
Login: pick a customer **by exact name** from a list. There's no password per customer; the only credential is the shared Oracle DB password (App.java:904-928).

| Operation | Rules (App.java) | DB writes |
|---|---|---|
| **View accounts** | Accounts via `account_ownership` | — |
| **Deposit** (452-503) | Branch must be **Full Service**; account must be one the customer owns; any parsed number accepted | `balance += amt`; insert `transaction('deposit')` |
| **Withdraw — checking** (575-595) | Any branch; rejected if `balance - amt <= 0` (re-prompts) | `balance -= amt`; insert `transaction('withdrawal')` |
| **Withdraw — savings** (541-574) | If `balance - amt < minimum_balance`: warn about the penalty and ask YES/NO. YES → `balance -= (amt - 50)` and **no** transaction row. Otherwise, if `balance - amt < 50` → rejected | normal path: `balance -= amt`; insert `transaction('withdrawal')` |
| **Open checking** (648-650) | Opening balance entered by user | `account('checking', bal, 0)`, `checking`, `account_ownership` |
| **Open savings** (636-647) | Interest 1.25. Tier from opening balance: `> 2000` → min 1000 / penalty 50; `> 1000 and < 2000` → 500 / 50; else → 100 / 25 | `account('savings', bal, 1.25)`, `savings`, `account_ownership` |
| **View cards** (846-875) | Debit: name, card id, linked account balance. Credit: rate, limit, running balance, balance due | — |
| **Open credit card** (718-731) | User picks the limit | `card('credit')`, `credit(18.0, limit, 0, 0)` |
| **Open debit card** (690-716) | Lists the customer's checking accounts, accepts any owned account ID | `card('debit', account_id)`, `debit` |
| **Take loan** (287-339) | Type `mortgage` or `unsecured` (case-insensitive, stored as typed). Tiers: `> 100000` → 5% / $500; `50000–100000` → 4% / $400; `25000–50000` → 3.75% / $350; `10000–25000` → 5% / $250; `1000–10000` → 5% / $100; else 6% / $50 (all bounds exclusive) | `loan` |
| **Pay loan** (341-393) | Choose loan and any owned account; any amount | `loan.amount -= p`; `balance -= p`; no transaction row |
| **Purchase — debit** (783-807) | Vendor chosen by exact name; rejected if `balance - amt <= 0` | `balance -= amt`; insert `purchase` |
| **Purchase — credit** (752-781) | Rejected if `amt > limit - running_balance` | `running_balance += amt`; insert `purchase` |

Behaviors to keep exactly as they are, unless a change is approved:
- Purchases and loan payments are **not** written to `transaction`.
- Opening an account doesn't record the opening balance as a transaction.
- `credit.balance_due` is never updated. There's no credit-card payment feature.
- The rates are hardcoded: savings 1.25, checking 0, credit 18.0.

## 3. Potential bugs (documented, NOT fixed — awaiting approval)

Per CLAUDE.md, none of these are changed. Each one needs explicit approval first.

| ID | Where | Observed behavior | Likely intent | Proposed fix / side effects |
|---|---|---|---|---|
| BUG-01 | Database.java:160 | `showPastPurchasesByCardId` selects from `Purchases`; the table is `Purchase`. Would fail, but it is never called | Query `Purchase` | Fix the name if a purchase-history view is built. No effect on existing flows |
| BUG-02 | App.java:552-561 | Savings penalty withdrawal subtracts `amount - 50`: the customer is charged **$50 less**, the penalty is hardcoded (ignores `savings.penalty`), and no transaction is recorded | Subtract `amount + penalty` and record the withdrawal | Changes balances on the penalty path. It could also take the balance below zero, so a floor rule is needed |
| BUG-03 | App.java:564-566 | "Balance below $50" check can never trigger (min balance is always ≥ $100), and its message says "less than 0" | Unclear | Leave as is or remove. Cosmetic |

| BUG-05 | App.java:638-646 | Savings opened with exactly $1,000 or $2,000 gets the lowest tier | Inclusive bounds | Use `>=`. Changes the tier only at the exact boundaries |
| BUG-06 | throughout | Zero and negative amounts are accepted (a negative deposit acts as a withdrawal, a negative credit limit is allowed, etc.) | Positive amounts only | Validate `amount > 0`. Rejects input that used to be accepted |

| BUG-08 | App.java:697-714 | Debit card creation shows only checking accounts but accepts a savings account ID | Checking only | Restrict to checking |
| BUG-09 | Database.java (autocommit) | Multi-step operations aren't atomic: a balance update followed by a failed transaction insert leaves partial data | All-or-nothing | Wrap each operation in one DB transaction (a Postgres function). Behavior is the same when nothing fails |
| BUG-10 | Database.java:599 | Credit purchase prints "Deposit successful." | Message text | Cosmetic. N/A in the web UI |

Also worth noting, though not bugs: checking accounts can never reach exactly $0.00 (`<= 0` is rejected), login is by name with no per-customer authentication, and duplicate customer names would make login ambiguous (`selectOneCustomerByName` returns the first match).
